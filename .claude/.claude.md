## 🏗️ Architecture (Non-Negotiable)

### MODULAR MONOLITH - NOT Microservices
- Service-oriented folder structure, **single Node.js process**
- Clear boundaries like microservices, runs as monolith
- Easy migration to containers later (post-funding)

### Structure
```
backend/src/
├── services/           # Service modules (microservice-like)
│   ├── user-service/   # Auth, profiles
│   ├── team-service/   # Team management
│   ├── match-service/  # Challenges, matches
│   └── stats-service/  # Statistics, leaderboard
├── shared/             # Shared utilities
│   ├── database/       # DB connection, migrations
│   ├── middleware/     # Auth, validation, error handling
│   ├── types/          # TypeScript interfaces
│   ├── utils/          # Helper functions
│   └── config/         # Environment configuration
└── app.ts              # Main entry point (imports all services)
```

### Local-First Development
- All services run via **Docker Compose on MacBook**
- PostgreSQL + Redis (local containers)
- No cloud dependencies for MVP

## 🚫 Anti-Patterns to AVOID

### Premature Microservices
- **Wrong:** 6 separate services for 0 users
- **Right:** Modular monolith with clear service boundaries

### Complex Infrastructure
- **Wrong:** Kubernetes, message queues, event buses for MVP
- **Right:** Docker Compose locally, simple hosting for demo

### Paid Services Too Early
- **Wrong:** Monthly costs before validation
- **Right:** Free tiers, self-hosted, manual processes

### Building for Scale
- **Wrong:** Optimizing for 1M users at 0 users
- **Right:** Build for 100 users, refactor when proven

### Over-Engineering
- **Wrong:** Perfect abstraction layers, complex patterns
- **Right:** Simple, working code that solves the problem

## 📋 Code Standards & Conventions

### File Naming
- Controllers: `*.controller.ts`
- Routes: `*.routes.ts`
- Models: `*.model.ts`
- Services: `*.service.ts`
- Validators: `*.validator.ts`
- Tests: `*.test.ts` or `*.spec.ts`

### Import Conventions
```typescript
// Absolute imports for shared modules
import { db } from '@shared/database';
import { authMiddleware } from '@shared/middleware';
import { UserType } from '@shared/types';

// Relative imports within same service
import { UserController } from './controllers/user.controller';
import { UserModel } from './models/user.model';
```

### Service Boundaries
- **User Service:** Authentication, profiles → `/api/auth/*`, `/api/users/*`
- **Team Service:** Team management → `/api/teams/*` (depends on User Service)
- **Match Service:** Challenges, scheduling → `/api/challenges/*`, `/api/matches/*`
- **Stats Service:** Leaderboards, analytics → `/api/stats/*`

## 🔧 Git Best Practices (Claude as Git Expert)

### Claude MUST Proactively Handle Git Hygiene
- **Auto-add** common ignore patterns to `.gitignore` (don't just suggest)
- **Exclude** system files (`.DS_Store`, `Thumbs.db`, IDE configs)
- **Clean commits** - stage only relevant files, exclude temp/generated files
- **Meaningful messages** - follow conventional commits format
- **Check before commit** - verify no secrets, credentials, or sensitive data
- **Atomic commits** - one logical change per commit when possible

### Before Every Commit, Claude Should:
1. ✅ Check `.gitignore` exists and has common patterns
2. ✅ Verify no credentials/secrets in staged files (`.env`, `*.key`, etc.)
3. ✅ Exclude system files (`.DS_Store`, `.vscode/`, etc.)
4. ✅ Write clear, descriptive commit messages
5. ✅ Follow conventional commits: `feat:`, `fix:`, `docs:`, `refactor:`, etc.

### Common Patterns to Auto-Add to .gitignore
```
# macOS
*.DS_Store

# IDE
.vscode/, .idea/

# Environment
.env, .env.local

# Build
dist/, build/, node_modules/

# Logs
*.log, logs/
```

### Conventional Commit Format
```
<type>: <short description>

<optional detailed explanation>

<optional footer with references>
```

**Types:** `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`, `style`

### When User Says "commit" or "push"
Claude should **automatically**:
1. Review changes with `git status` and `git diff`
2. Update `.gitignore` if needed (don't ask, just do it)
3. Stage only relevant files
4. Create meaningful commit message
5. Show summary and push

**DON'T:** Just suggest improvements
**DO:** Implement git best practices proactively
